# Jev Test — ZCode

本 skill 管理测试与取证。目标**不是**最大化截图数量，而是收集**能证明用户需求确实被验证的最小高价值证据集**。

Jev 是辅助决策模型；真实测试结果才是事实来源。

## 0. 尊重规划/执行状态

若 `grill-me` 仍处 PLANNING_LOCKED 且用户未明确授权执行：

- 不跑有副作用的测试、不改源码/数据库、不部署
- 不造测试数据（明确无害的除外）
- 只做只读的测试规划

`jev-test` **不得**绕过 `grill-me` 的执行锁。

## 1. 项目证据规则优先

测试规划前先找项目级规则：`test-evidence-rules.md`（根目录 / docs/ / validation/）、AGENTS.md、README 中的验收标准。存在则视为项目约束，可叠加强制测试点、强制截图、禁测生产、日志/数据库证据、命名规范、证据输出目录等。**不发明不存在的项目规则。**

## 2. 先建需求-测试矩阵

实质性测试前，对需要证明的重要需求建内部矩阵：需求 / 风险 / 测试方法 / 预期结果 / 候选证据 / 是否需要用户可见证明。

不要盲目穷举测试，按优先级排：

1. 用户验收标准
2. 安全关键行为
3. 数据完整性
4. 易回归行为
5. 失败/恢复路径
6. 用户可见的最终行为

## 3. 候选检查点

检查点**不是**每个动作。好的检查点：

- 关键业务规则生效
- 危险操作被正确拦截
- 失败路径行为正确
- 重要状态迁移完成、数据正确落库
- 重启/恢复正常
- 回归测试先复现再验证修复
- 用户可见结果达到预期终态
- 安全边界被强制执行

坏检查点：打开文件、无验收价值的中间页跳转、每次命令执行、每次点击、每个 setup 步骤、同状态重复截图。

## 4. 批量 Jev 检查点评审（强制）

实质性测试时，把候选检查点**一次批量**送 `jev_review`（`checkpoints` 传 JSON 数组，每项 `{checkpoint, why}`；≤20 个/批），不要逐条调用。每个检查点确认三件事：

- **重要性**（importance）：critical / high / normal / low
- **留证决策**（capture）：must_capture / recommended_capture / no_capture
- **最佳证据类型**（evidence_type）：screenshot / video / console_output / test_output / log / api_response / database_query / file_diff / configuration / network_trace / no_extra_evidence

再为每项确定**证据目标**：证据必须实际展示什么——页面标题、关键字段值、成败状态；日志中的事件与决策；操作前后的精确行/状态。

**离线回退**：返回 `jev: "offline"` 时按其 `fallback_advice` 自行评定（重要性看验收价值与失败后果；只有"不留证据就无法证明"的检查点才 must_capture；优先结构化证据），并在报告中注明"Jev 离线，自行评定"。

## 5. 截图规则

**该截图**：用户可见的最终 UI 结果、错误弹窗/视觉故障、布局渲染问题、权限/访问状态、重要流程状态、浏览器行为、报表/仪表盘结果、用户要肉眼复核的证据。

**不该截图**（改用结构化证据）：数据库一致性（用 database_query + test_output）、后端状态、API payload 正确性、日志解析、数值断言、pytest 结果原文。

非视觉事实一律优先结构化证据。

## 6. 只取能证明问题的证据

对每个 must_capture / recommended_capture 项记录：检查点 / 为什么重要 / 证据类型 / 精确证据目标 / 实际观察结果。

一张截图能同时证明两个检查点就只截一张；证不干净就分开截。避免冗余截图。

## 7. 失败也是证据

重要测试失败时不要急于掩盖或重跑：先留证（错误状态、日志、异常、API 响应、失败断言；UI 失败配截图），再诊断修复，修复后**重跑同一测试**并留通过证据，形成：

**BEFORE/FAILURE → FIX → AFTER/PASS**

只保留对解释或验证结果有用的证据。

## 8. Jev 覆盖审查

一个有意义的测试阶段结束后做第二轮评审，输入：需求、实际执行的测试、通过/失败、已有证据、跳过的测试、未解决风险。要找出：

- 缺失的关键测试路径 / 失败路径 / 恢复测试
- 弱证据（证不了它声称的结论）
- 冗余证据
- 没有任何证明的需求

**不要因为"现有测试全绿"就宣布覆盖完整。**

## 9. 证据充分性四态

- `VERIFIED`：有合适测试 + 观察到预期结果 + 证据充分
- `PARTIALLY_VERIFIED`：有证据但重要分支/条件未测
- `NOT_VERIFIED`：无充分测试/证据
- `BLOCKED`：环境/凭证缺失、外部系统不可用、生产安全约束、待用户决策

**禁止**把 PARTIALLY_VERIFIED / BLOCKED 当作 VERIFIED 汇报。

## 10. 测试输出格式

实质性测试阶段结束按此汇报：

```
## 测试结果

### 1. <测试点>
- 状态：通过 / 失败 / 部分验证 / 未验证 / 阻塞
- Jev 重要性：
- 验证方式：
- 证据类型：
- 关键结果：
- 是否需要截图：
- 证据位置：

### 2. …

## Jev 覆盖检查
- 已充分验证：
- 仍缺少：
- 建议补测：
- 可删除的重复证据：

## 总体状态
- VERIFIED / PARTIALLY_VERIFIED / NOT_VERIFIED / BLOCKED
```

此处**不得**宣布整个任务完成——最终完成判定属于 `jev-complete`。

## 11. 效率规则

10 个候选检查点 → **一次批量**评审。禁止逐检查点调用 Jev 浪费往返。

## 12. 安全

**永不发送给 Jev**：API key、密码、Token、Cookie、私钥、数据库凭证、密钥、敏感生产 payload——改发摘要。

Jev 建议永远不覆盖：用户授权、ZCode 权限机制、测试安全、生产保护。
